### 1. Non-Blocking Pipelines with `CompletableFuture`

`CompletableFuture` provides a functional, non-blocking asynchronous programming model supporting task composition and exception recovery callbacks.

```java
import java.util.concurrent.CompletableFuture;

public class AsyncPipeline {
    public static void main(String[] args) {
        CompletableFuture.supplyAsync(() -> fetchOrderData())
            .thenApply(order -> calculateTax(order))
            .thenAccept(finalTotal -> System.out.println("Final Invoice: $" + finalTotal))
            .exceptionally(ex -> {
                System.err.println("Pipeline failed: " + ex.getMessage());
                return null;
            });
    }

    private static String fetchOrderData() { return "Order#101"; }
    private static double calculateTax(String order) { return 105.50; }
}
```

### 2. Virtual Threads (Project Loom, Java 21+)

Prior to Java 21, every Java thread (`java.lang.Thread`) was a 1:1 wrapper around an **OS platform thread**, requiring ~1MB of memory and expensive kernel context switching.

**Virtual Threads** (JEP 444) are lightweight threads managed directly by the JVM.

```
  Virtual Threads (Millions) ──► Carrier Threads (JVM Pool) ──► OS Kernel Threads (Hardware Cores)
```

| Dimension | Platform / OS Threads | Virtual Threads (Java 21+) |
| :--- | :--- | :--- |
| **OS Mapping** | 1:1 OS Thread | M:N Carrier Thread pool |
| **Memory Footprint** | ~1 MB per thread | ~200 Bytes per thread |
| **Max Capacity** | Thousands per JVM | Millions per JVM |
| **Use Case** | CPU-bound computation | I/O-bound blocking calls (DB queries, REST calls) |

```java
// Launching 10,000 concurrent Virtual Threads effortlessly
try (var executor = java.util.concurrent.Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        final int id = i;
        executor.submit(() -> {
            Thread.sleep(1000); // Non-blocking park of virtual thread
            return id;
        });
    }
} // Auto-joins and closes executor
```

> [!WARNING]
> **Carrier Thread Pinning**: Avoid holding `synchronized` locks during blocking I/O calls inside Virtual Threads, as it pins the virtual thread to its underlying carrier thread. Use `ReentrantLock` instead.

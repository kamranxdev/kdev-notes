## 🔒 Relational Integrity Constraints

Constraints are declarative rules configured at schema definition time (`CREATE TABLE` / `ALTER TABLE`). The database storage engine enforces these rules on every insert, update, and delete to guarantee referential integrity and data validity.

```sql
CREATE TABLE departments (
    dept_id     INT PRIMARY KEY,
    dept_name   VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE employees (
    emp_id      INT PRIMARY KEY,
    emp_name    VARCHAR(100) NOT NULL,
    salary      NUMERIC(10, 2) CHECK (salary > 0),
    dept_id     INT,
    email       VARCHAR(150) UNIQUE,
    status      VARCHAR(20) DEFAULT 'ACTIVE',
    CONSTRAINT fk_emp_dept FOREIGN KEY (dept_id) 
        REFERENCES departments(dept_id) 
        ON DELETE SET NULL
);
```

### Constraint Mechanics Matrix

| Constraint | Primary Purpose | Nullability Rule | Indexing Impact |
| :--- | :--- | :--- | :--- |
| **PRIMARY KEY** | Uniquely identifies each record in the table. | Strictly `NOT NULL` | Implicitly creates a **Clustered / Primary Index** |
| **FOREIGN KEY** | Enforces referential integrity link to a parent table primary key. | Can be `NULL` (unless explicitly declared `NOT NULL`) | Best practice: Add a manual Non-Clustered index for fast joins |
| **UNIQUE** | Prevents duplicate non-null entries in a column/group of columns. | Permits multiple `NULL` entries (since `NULL != NULL`) | Implicitly creates a **Unique Non-Clustered Index** |
| **NOT NULL** | Prevents missing/unknown values from being saved into the field. | Rejects `NULL` | None |
| **CHECK** | Validates that column data satisfies a boolean expression. | Expression evaluates to `TRUE` or `UNKNOWN` (passes `NULL`) | None |
| **DEFAULT** | Provides fallback literal/expression value if omitted on `INSERT`. | N/A | None |

## 🔄 Foreign Key Delete Actions

When a parent row in a referenced table is deleted, foreign key cascading rules define child row behavior:

* `ON DELETE RESTRICT` (Default): Throws a referential integrity violation error and blocks deletion of the parent row if any child rows exist.
* `ON DELETE CASCADE`: Automatically deletes all child rows linked to the deleted parent row.
* `ON DELETE SET NULL`: Automatically updates foreign key columns in child rows to `NULL` when the parent row is removed.

## 📐 Database Normalization (1NF to BCNF)

Normalization is the process of structuring relational schema tables to eliminate data redundancy, update anomalies, insertion anomalies, and deletion anomalies.

* **Analogy**: *Organizing your clothes closet.* Instead of dumping shoes, shirts, coats, and socks into one giant pile (unnormalized table), you put shirts on hangers, shoes in shoe racks, and socks in labeled drawers (normalized relational tables).

```
   Unnormalized Data  ──►  1NF (Atomic Values)  ──►  2NF (Remove Partial Dependencies)
                                                                 │
   BCNF (Strict Superkey)  ◄──  3NF (Remove Transitive Dependencies) ◄┘
```

### 1. First Normal Form (1NF)
* **Rule**: Every column must contain **atomic values** (indivisible single values). No repeating groups, arrays, or comma-separated lists inside cells. Every row must be uniquely identifiable.

```sql
-- VIOLATES 1NF (Multi-valued comma-separated hobbies)
-- emp_id | emp_name | hobbies
-- 101    | Alice    | "Reading, Swimming, Chess"

-- COMPLIES WITH 1NF (Atomic rows)
-- emp_id | emp_name | hobby
-- 101    | Alice    | Reading
-- 101    | Alice    | Swimming
-- 101    | Alice    | Chess
```

### 2. Second Normal Form (2NF)
* **Rule**: Table must be in **1NF**, and all non-key attributes must depend on the **entire primary key** (eliminates **partial functional dependency** in composite key tables).

### 3. Third Normal Form (3NF)
* **Rule**: Table must be in **2NF**, and no non-key attribute can depend on another non-key attribute (eliminates **transitive functional dependency**). Every non-key column must depend on *the key, the whole key, and nothing but the key*.

```
Transitive Dependency Example:
Emp_ID (Key) ──► Dept_ID (Non-Key) ──► Dept_Name (Non-Key)
Solution: Move Dept_ID and Dept_Name into a separate Departments table.
```

### 4. Boyce-Codd Normal Form (BCNF)
* **Rule**: A stricter version of 3NF. For every non-trivial functional dependency $X \rightarrow Y$, $X$ must be a **superkey**.

## ❓ Conceptual Quizzes

<Quiz question="What happens if a UNIQUE constraint is placed on a column containing multiple NULL values?" options={["The database throws a duplicate key error on the second NULL.", "The UNIQUE constraint permits multiple NULLs because NULL != NULL in SQL logic.", "The database converts NULLs into empty strings.", "UNIQUE automatically implies NOT NULL."]} answerIndex={1}>
In SQL standards, `NULL` represents an unknown value. Because comparing two unknown values (`NULL = NULL`) yields `UNKNOWN` (not `TRUE`), multiple `NULL` values do not violate a `UNIQUE` constraint.
</Quiz>

## 💻 Practice Problems

<Problem title="Problem: Refactoring Transitive Dependencies to 3NF">
<ProblemDescription>
Given a single table `employee_project`:
`(emp_id, project_id, project_name, project_location)` where `(emp_id, project_id)` is a composite primary key. `project_name` depends solely on `project_id`. Identify the normalization violation and refactor into 3NF.
</ProblemDescription>
<ProblemSolution>
The table violates **2NF** because `project_name` and `project_location` depend partially on `project_id` rather than the complete composite key `(emp_id, project_id)`.

Refactored 3NF Design:

```sql
-- Table 1: Projects (Project Entity)
CREATE TABLE projects (
    project_id       INT PRIMARY KEY,
    project_name     VARCHAR(100) NOT NULL,
    project_location VARCHAR(100)
);

-- Table 2: Employee Project Assignments (Junction Table)
CREATE TABLE employee_projects (
    emp_id      INT NOT NULL,
    project_id  INT NOT NULL,
    PRIMARY KEY (emp_id, project_id),
    FOREIGN KEY (project_id) REFERENCES projects(project_id) ON DELETE CASCADE
);
```
</ProblemSolution>
</Problem>

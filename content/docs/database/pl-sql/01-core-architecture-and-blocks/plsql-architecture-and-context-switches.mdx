## 🏛️ The Dual-Engine Architecture

PL/SQL code executes directly inside the Oracle database server instance. However, the database server contains **two distinct execution engines**:

1. **The PL/SQL Engine**: Responsible for procedural control flow, evaluating variable assignments, `IF-THEN-ELSE` conditionals, loops, and exception handling blocks.
2. **The SQL Engine**: Responsible for parsing SQL statements, consulting the query optimizer, managing transaction locks, and reading physical disk pages or buffer pool RAM.

```
                         Oracle Database Server Instance
 ┌─────────────────────────────────────────────────────────────────────────────┐
 │                                                                             │
 │  ┌───────────────────────────────┐        SQL Statements        ┌─────────┐ │
 │  │        PL/SQL Engine          ├─────────────────────────────►│   SQL   │ │
 │  │  (Loops, IFs, Assignments)    │◄─────────────────────────────┤ Engine  │ │
 │  └───────────────────────────────┘           Data Rows          └────┬────┘ │
 │                                                                        │    │
 └────────────────────────────────────────────────────────────────────────┼────┘
                                                                          ▼
                                                                  [( Disk Blocks )]
```

## 🚶 The Context Switch Bottleneck

A **Context Switch** occurs every time execution control transitions from the PL/SQL engine to the SQL engine to process a SQL query or statement, and returns back with the data payload.

* **Analogy**: *A bank manager and a vault clerk.*
  * The bank manager (**PL/SQL Engine**) processes logic, checks applicant rules, and writes notes.
  * The vault clerk (**SQL Engine**) opens physical vault drawers to fetch document folders.
  * **Row-by-Row Bottleneck**: If the manager runs a loop 10,000 times, walking over to the clerk for a single folder on every iteration, the manager wastes 99% of their day walking back and forth (Context Switch Overhead)!

```sql
-- SLOW: 10,000 Context Switches executed inside a row-by-row cursor loop
DECLARE
  CURSOR c_emps IS SELECT employee_id FROM employees;
BEGIN
  FOR r IN c_emps LOOP
    -- Context switch on EVERY iteration!
    UPDATE employees SET salary = salary * 1.05 WHERE employee_id = r.employee_id;
  END LOOP;
END;
/
```

> [!WARNING]
> High numbers of row-by-row context switches degrade CPU performance and increase latch contention. Use **Bulk Operations (`BULK COLLECT` and `FORALL`)** to transfer data in single array batches!

## 🧱 Block Classification: Anonymous vs Stored Blocks

PL/SQL code units are written as structured blocks:

1. **Anonymous Blocks**: Unnamed PL/SQL blocks compiled and executed on the fly by client scripts (SQL*Plus, SQL Developer). They are not saved into the database data dictionary.
2. **Stored Procedures & Functions**: Named blocks compiled once and stored as binary schema objects in the database dictionary. Can be invoked by external applications or backend APIs.
3. **Packages**: Encapsulated groups of related procedures, functions, types, and variables stored together under a single schema header.

## 💻 Practice Problems

<Problem title="Problem: Converting Row-by-Row Update to Set-Based SQL">
<ProblemDescription>
Refactor a slow PL/SQL anonymous block that iterates through all active employees to update their status from `INACTIVE` to `ARCHIVED` row-by-row into a single set-based statement to eliminate context switching.
</ProblemDescription>
<ProblemSolution>
Replace the PL/SQL loop with a single declarative SQL statement:

```sql
-- Replaces row-by-row context switching loop with 1 single SQL engine call
UPDATE employees
SET status = 'ARCHIVED'
WHERE status = 'INACTIVE';
```
</ProblemSolution>
</Problem>

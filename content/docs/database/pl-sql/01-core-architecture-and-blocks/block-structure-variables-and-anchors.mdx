## 🏗️ The 4-Section PL/SQL Block Structure

Every PL/SQL code block is constructed using up to four distinct functional sections:

```sql
DECLARE       -- [OPTIONAL] Variable declarations, cursor definitions, custom types
  v_emp_id    NUMBER(6) := 101;
  v_emp_name  employees.first_name%TYPE; -- Scalar Anchor
BEGIN         -- [MANDATORY] Executable statements, procedural logic, SQL calls
  SELECT first_name INTO v_emp_name
  FROM employees
  WHERE employee_id = v_emp_id;
  
  DBMS_OUTPUT.PUT_LINE('Employee Name: ' || v_emp_name);
EXCEPTION     -- [OPTIONAL] Runtime exception handlers
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('No employee found with ID: ' || v_emp_id);
  WHEN OTHERS THEN
    DBMS_OUTPUT.PUT_LINE('Unexpected Error: ' || SQLERRM);
END;          -- [MANDATORY] Marks the end of the block
/
```

## ⚓ Variable Anchoring: `%TYPE` and `%ROWTYPE`

Hardcoding variable data types (e.g., `v_name VARCHAR2(50)`) creates maintenance risk: if an administrator alters the underlying table column width to `VARCHAR2(100)`, the PL/SQL code will crash with numeric or value errors!

PL/SQL solves this using **Data Anchoring**:

### 1. Scalar Attribute Anchoring (`%TYPE`)
* Copies the data type, precision, and nullability rules of an existing database column dynamically.
* **Analogy**: *Buying a key blank engineered to copy a specific lock design.* If the lock changes, your key template updates automatically on next compile.

```sql
v_salary  employees.salary%TYPE;
```

### 2. Record Structural Anchoring (`%ROWTYPE`)
* Copies the entire structural definition of a table row into a composite record variable in memory.
* **Analogy**: *Cloning a master room layout blueprint card.*

```sql
v_emp_rec  employees%ROWTYPE;
-- Access individual fields using dot notation
v_emp_rec.salary := 75000;
```

## 🚨 Exception Handling Mechanics

Exceptions trap runtime errors raised during statement execution:

### 1. Predefined Oracle Exceptions
* `NO_DATA_FOUND`: Raised when a `SELECT INTO` statement returns zero rows.
* `TOO_MANY_ROWS`: Raised when a scalar `SELECT INTO` statement returns multiple rows.
* `ZERO_DIVIDE`: Raised when attempting to divide a number by zero.
* `DUP_VAL_ON_INDEX`: Raised when an insert/update violates a `UNIQUE` constraint.

### 2. User-Defined Exceptions & Custom Codes
Use `RAISE_APPLICATION_ERROR(error_number, error_message)` to report business logic violations (error numbers must range between `-20000` and `-20999`):

```sql
DECLARE
  e_invalid_salary EXCEPTION;
  v_sal NUMBER := -500;
BEGIN
  IF v_sal <= 0 THEN
    RAISE e_invalid_salary;
  END IF;
EXCEPTION
  WHEN e_invalid_salary THEN
    RAISE_APPLICATION_ERROR(-20001, 'Salary must be greater than zero!');
END;
/
```

## 💻 Practice Problems

<Problem title="Problem: Safe Record Retrieval Procedure">
<ProblemDescription>
Write a PL/SQL block that accepts an `p_emp_id`, fetches the entire employee row into a `%ROWTYPE` record, prints their department ID and salary, and safely handles `NO_DATA_FOUND` without crashing.
</ProblemDescription>
<ProblemSolution>
```sql
DECLARE
  v_emp_id employees.employee_id%TYPE := 999;
  v_emp_rec employees%ROWTYPE;
BEGIN
  SELECT * INTO v_emp_rec
  FROM employees
  WHERE employee_id = v_emp_id;

  DBMS_OUTPUT.PUT_LINE('Dept: ' || v_emp_rec.department_id || ', Sal: ' || v_emp_rec.salary);
EXCEPTION
  WHEN NO_DATA_FOUND THEN
    DBMS_OUTPUT.PUT_LINE('Employee ID ' || v_emp_id || ' does not exist in schema.');
END;
/
```
</ProblemSolution>
</Problem>
